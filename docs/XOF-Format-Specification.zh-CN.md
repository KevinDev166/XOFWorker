# XOF — Xiangqi Open Format（象棋开放格式）

[English](XOF-Format-Specification.md) | **简体中文** | [Tiếng Việt](XOF-Format-Specification.vi.md)

**规范，版本 1.0（2026-11-16）**

XOF 是一种用于保存象棋对局的纯文本文件格式。它可以记录着法、多层嵌套的变着、每步棋的注释、
每步棋的时间戳，以及您想添加的任何对局信息。它取代 2025 年的越南语草案
（`XOF Format Specifications.pdf`）。两者不一致之处，以本文档为准（见 §3.9）。

## 1. 现有格式存在的问题

一份棋谱包含两个层面：**着法记法**（一步棋怎么写）和**文件格式**（整盘棋连同对局信息、
变着和注释怎么保存）。如今这两个层面都存在严重问题。

### 1.1 着法记法：有歧义、不统一、依赖规则

传统记法（`C2=5`、`N8+7`、炮二平五、马8进7 …）是棋手们实际使用的记法，在棋盘上很容易想象。
但每个棋协都有自己的写法。我们查阅了已出版的规则书（WXF 2018、AXF 1996、越南 2004 年与
2021 年规则、中国 2020 年规则），发现了以下问题：

1. **省略前/后标记会使着法产生歧义。** 一本 AXF 书中印有 `C9+1`，而在该局面中蓝方在第 9 路
   上有*两个*炮，相隔两行，并且*两个*都能前进一步。没有人能判断是哪一个炮走的；按 WXF
   写法应为 `+C+1`。这样的着法只能靠运气来判断，即恰好只有其中一个棋子有合法着法。因此读者
   （无论是人还是程序）需要局面和合法着法生成器才能读懂这段文字。
2. **“前 / 中 / 后”只能处理三个棋子。** 同一路上最多可以有五个兵。传统标记无法表示第 4 个和
   第 5 个兵。
3. **同样的文字在不同规则下意思不同。** 例如，`P2-5` 在越南 2004 年记法中是*平*，而在 2021 年
   记法中同一个字符串却是*退*。要读懂一盘棋，您必须知道（或猜测）它是按哪本规则书记录的，
   而且整盘棋都必须一致。
4. **两个字符的棋子符号**（如越南 2004 年的 `Tg`）使着法长短不一，妨碍简单解析。
5. **官方规则书本身不一致。** WXF 规则书对同一情况（同一路上有两个车）有时写成 `R4-2`，有时
   写成 `+R-2`。仕和相用路数而不用前/后。有一本书对蓝方时而用大写、时而用小写。没有任何
   规则说明当*两*路上各有叠兵时该怎么写。
6. **数字和字符体系混用。** 中文棋谱中红方的路数写作 一…九，黑方写作 1–9，有时还用全角数字
   １…９。繁体字和简体字也混在一起（車/车、進/进、後/后）。
7. **印刷错误无法从文字中发现。** 我们在一本 AXF 书中发现 13 幅图的着法有误（棋子字母或数字
   错误）。只有在棋盘上重放这些着法时才会暴露出来。

ICCS 等坐标记法（`h2e2`）没有歧义，但人很难读懂，几乎没有棋手用它记录或思考。

### 1.2 文件格式：封闭、扁平或定义松散

- **封闭的二进制格式。** 大多数象棋软件用自己的二进制格式保存对局（XQF、CCBridge CBL/CBR …）。
  其中一些经过加密或没有公开文档。只有写入文件的程序才能读取。程序一旦消失，棋谱库也随之
  消失。
- **象棋 PGN 没有变着。** 实际上，您遇到的象棋 PGN 文件从来不包含分支。分析——带注释棋谱中
  最有价值的部分——就此丢失。
- **象棋 PGN 的着法文字没有标准。** 每个写入程序都使用自己的棋子字母、语言和记法（见 §1.1）。
  文件本身不说明使用哪套符号，因此读者在导入前必须手动指定。
- **PGN 很难解析好。** 变着、注释、回合数和评注全部挤在同一个自由格式的文本流中。写一个正确
  的读取器所需的工作量远超应有的程度。
- **没有地方记录着法时间。** 电子棋盘和网络对弈会记录每步棋*何时*走出，但没有标准的位置来
  保存它。

## 2. 世界需要一种更好的格式：为什么选择 XOF

**XOF** 是 **Xiangqi Open Format**（象棋开放格式）的缩写。目标是：人人能读，人人能写，没有
任何歧义。

| 现有问题 | XOF 的做法 |
|---|---|
| 封闭的二进制格式 | 纯 UTF-8 文本。任何文本编辑器都能打开，不用软件也能读懂。 |
| 着法有歧义（§1.1 第 1、2、5 条） | **始终写出路数。** 当两个或更多同类棋子在同一路上时，**必须**加上位置前缀 `1`…`5`。这能处理全部五个兵，每步棋都能根据局面无需猜测地解码。 |
| 同样的文字在不同规则书中意思不同（第 3 条） | 每个符号只有一个含义：`+` 进，`-` 退，`=` 平。这永远不依赖于规则书。 |
| 棋子字母因语言而异（第 4、6 条） | 每盘棋声明自己的 **Pieces Key**（棋子符号表，7 个单字符符号）。可以使用英文、越南文、中文或任何其他语言，读取时都没有歧义。 |
| 没有变着（PGN） | 变着深度不限，同一步棋的备选数量也不限。 |
| 难以解析 | **一步棋 = 一行**，各列以制表符分隔。读取器只需一个按行拆分器加一个小型递归函数（§4）。 |
| 没有着法时间 | 每一行着法都有自己的时间戳列。 |
| 注释混在着法流中 | 每一行着法都有自己的注释列。 |
| 对局信息格式随意 | 12 个必需的头字段名，再加上任意数量的自定义头字段。 |

纯文本行还带来其他好处：

- **便于版本控制。** 每行一步棋，`git diff` 的输出清晰。修改一步棋或一条注释只显示为一行变化。
- **可用标准工具搜索。** 用 `grep` 或任何文本搜索工具都能在成千上万个文件中查找着法、注释或
  棋手。
- **便于存入数据库。** 整盘棋就是一个字符串。可以存入一个文本列，再用同一个读取器解析（§3.8）。
- **便于手工修正。** 书中的印刷错误可以直接在文本编辑器中改正。

## 3. XOF 格式规范

关键词 **必须**（MUST）、**不得**（MUST NOT）、**应当**（SHOULD）、**不应**（SHOULD NOT）和
**可以**（MAY）的含义与 RFC 2119 相同。

### 3.1 编码与换行符

- 文件**必须**使用 **UTF-8** 编码。写入程序**不应**写入 BOM。
- 换行符**可以**是 `\r\n`、`\n` 或 `\r`。读取程序**必须**接受这三种。
- 读取程序**必须**忽略空行。读取程序在解释每一行之前**应当**去掉行首和行尾的空白。不要去掉
  着法行*内部*的制表符，因为它们用来分隔各列。

### 3.2 文件结构

一个文件包含一盘或多盘**对局**。每盘对局有一个**头部区**和一个**着法区**：

```
<第 1 盘的头部区>
---------                       ← 区段分隔符：正好 9 个短横线
<第 1 盘的着法区>
------------------              ← 对局分隔符：正好 18 个短横线
<第 2 盘的头部区>
---------
<第 2 盘的着法区>
------------------
```

- **区段分隔符**是正好由 **9** 个短横线组成的一行（`---------`）。
- **对局分隔符**是正好由 **18** 个短横线组成的一行（`------------------`）。写入程序**必须**
  在每盘对局**之后**写入它，包括最后一盘。它永远不会出现在文件开头。
- 读取程序**应当**仍然接受最后一盘对局后面没有对局分隔符的情况。
- 任何头字段值或注释都**不得**包含连续 9 个或更多的短横线，否则读取程序可能把它当成分隔符。

### 3.3 头部区

每行一个头字段：

```
<Header Name>: <Header Value>
```

- 名称和值之间用**冒号**（`:`）分隔。两者首尾的空白都会被忽略。
- **头字段名或值不得包含冒号。** 如果写入程序需要在头字段中保存时间，必须把冒号换成其他字符
  （如 `20?53?00` 或 `20.53.00`）。着法时间戳不受影响，因为着法行使用制表符（§3.4）。
- 值**可以**为空。许多旧书中的对局没有日期、地点或棋手。

**必需的头字段。** 每盘对局**必须**包含以下 12 个头字段名，即使值为空也一样。写入程序**应当**
按以下顺序写出：

| 头字段名 | 含义 |
|---|---|
| `Event` | 赛事或比赛名称（对于书中的局面，则为题目名称） |
| `Address` | 对局地点 |
| `Date` | 对局日期，推荐格式 `YYYY-MM-DD` |
| `Round` | 轮次，用于分轮进行的比赛 |
| `Game Number` | 该局在本轮或本场比赛中的编号 |
| `Red Player` | 红方：可以是人、引擎、机器人… |
| `Blue Player` | 蓝方（很多书称为“黑方”） |
| `Red Team` | 红方所属的队伍、俱乐部或棋协 |
| `Blue Team` | 蓝方所属的队伍、俱乐部或棋协 |
| `Starting FEN` | 用 FEN 表示的起始局面（见下文） |
| `Result` | `1-0` 红胜，`0-1` 蓝胜，`1/2-1/2` 和棋，`*` 未知或未结束 |
| `Pieces Key` | 着法文字中使用的棋子符号（§3.5） |

标准开局的 `Starting FEN` 为：

```
rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w - - 0 1
```

让子局、残局和排局使用各自的局面。FEN 中的走子方（`w` = 红，`b` = 蓝）决定由谁走第 1 步。

**自定义头字段。** 在必需的头字段之后，对局**可以**包含任意数量遵循同样 `Name: Value` 规则的
额外头字段（如 `ECCO`、`Commentator`、`Time Control`、`Source`）。读取程序**必须**读取并保留
**所有**头字段，包括它不认识的那些。

### 3.4 着法区

每行记录**一方的一步棋**（一个半回合，ply）。着法行有 6 列，以**制表符**分隔：

```
[ML|VA] <TAB> [Number] <TAB> [Move] <TAB> [R|B] <TAB> [Date time] <TAB> [Comment]
```

| 列 | 内容 |
|---|---|
| 1 | 主线着法写 `ML`，变着中的着法写 `VA` |
| 2 | 半回合序号，从 1 开始。每行是一个半回合，所以红方和蓝方各有自己的序号（1 红，2 蓝，3 红…）。 |
| 3 | 着法，按 §3.6 的方式并使用本局的 Pieces Key 书写 |
| 4 | 走这步棋的一方：`R` 红，`B` 蓝 |
| 5 | 走这步棋的时间，**可以**为空。推荐格式 `YYYY-MM-DD HH:MM:SS`（这里允许使用冒号）。适用于来自电子棋盘或网络对弈的对局，例如用来研究棋手的走棋速度。 |
| 6 | 对这步棋的注释，**可以**为空。**不得**包含制表符或换行符，写入程序必须把它们换成空格。 |

第 5、6 列可以为空，但写入程序**应当**始终写出全部 6 列（空列就是连续的制表符）。读取程序
**必须**接受只有前 4 列的行。

示例（英文 Pieces Key）：

```
ML	1	C2=5	R	2025-07-08 20:53:00	Central cannon
```

**对局结果只保存在 `Result` 头字段中。** 写入程序**不得**在最后一步棋之后添加结果行（`1-0`、
`0-1` …）。着法区以最后一行着法（或 `VARIANT]`）结束，随后是对局分隔符。

### 3.5 Pieces Key（棋子符号表）

`Pieces Key` 头字段以 `<棋子名> = <符号>` 对的形式列出 7 种棋子各自的符号，用逗号分隔，顺序
如下：

```
Pieces Key: King = K, Assistant = A, Elephant = E, Rook = R, Cannon = C, Knight = N, Pawn = P
```

- 棋子名是固定的英文单词：`King`（帅/将）、`Assistant`（仕/士）、`Elephant`（相/象）、
  `Rook`（车）、`Cannon`（炮）、`Knight`（马）、`Pawn`（兵/卒）。
- 每个符号**必须**是**正好一个字符**，且 7 个符号**必须**互不相同。
- 符号**不得**是数字、`+`、`-`、`=`、制表符或空白。拉丁字母**应当**使用大写。
- 双方使用相同的符号。由第 4 列（`R` / `B`）表明是哪一方走棋。

推荐的符号表：

| 语言 | Pieces Key 的值 |
|---|---|
| 英文 | `King = K, Assistant = A, Elephant = E, Rook = R, Cannon = C, Knight = N, Pawn = P` |
| 越南文 | `King = T, Assistant = S, Elephant = V, Rook = X, Cannon = P, Knight = M, Pawn = C` |
| 中文（简体，双方都用红方的字） | `King = 帅, Assistant = 仕, Elephant = 相, Rook = 车, Cannon = 炮, Knight = 马, Pawn = 兵` |

只要遵守上述规则，任何其他符号组都有效。读取程序绝不能自行假定符号表，必须始终使用对局中
声明的符号表。

### 3.6 着法文字

一步棋的写法为：

```
[position prefix] <piece> <street> <sign> <number>
```

即：[位置前缀] <棋子> <路数> <符号> <数字>

- **路数**按象棋的惯例，**从各自一方的右手边起编为 1 到 9**。红方从红方的右边数起，蓝方从
  蓝方的右边数起。
- **符号**（在所有语言中固定不变）：
  - `+` **进**：向对方移动
  - `-` **退**：向己方移动
  - `=` **平**：沿同一行横向移动
- **符号后面的数字：**
  - **车、炮、兵、帅**：在 `+` / `-` 之后表示**移动的步数（行数）**；在 `=` 之后表示棋子
    **到达的路数**。
  - **马、相、仕**：在 `+` / `-` 之后表示棋子**到达的路数**。这些棋子永远不会平移，所以对它们
    永远不使用 `=`。

示例（越南文符号表：`P` 炮，`M` 马）：

| 着法 | 含义 |
|---|---|
| `P2=5` | 第 2 路的炮平到第 5 路（炮二平五） |
| `M8+7` | 第 8 路的马进到第 7 路（马八进七） |
| `P8-2` | 第 8 路的炮退 2 步（炮八退二） |

**同一路上有多个同类棋子。** 当同一方的两个或更多同类棋子位于**同一路**时，着法**必须**以
`1` 到 `5` 的位置前缀开头：

- `1` 表示**离己方底线最远**的棋子（最靠前的那个），然后是 `2`、`3`、`4`，`5` 表示**离己方
  底线最近**的那个。
- 这适用于仕、相、车、炮、马以及最多五个兵。路数仍然要写出。
- 示例（英文符号表）：`1C4+2` 是第 4 路的前炮进 2 步。`2A4+5` 是第 4 路的后仕进到第 5 路。
  `3P5=4` 是第 5 路的第三个兵平到第 4 路。
- 当棋子独自在其所在路上时，**不得**写前缀。

由于路数始终写出且前缀是必需的，**一段着法文字恰好对应棋盘上的一步棋**。即使两条不同的路上
各有叠子，这一点也同样成立。

### 3.7 变着

变着是对其**紧前一步**着法的替代。下面的例子取自一个真实的残局文件，使用越南文符号表
（`S` 仕，`P` 炮）：

```
ML	7	C7+1	R
ML	8	1S4-5	B			← 主线第 8 步
[VARIANT
VA	8	2S4+5	B			← 第 8 步的替代着法
VA	9	P4=5	R
VARIANT]
ML	9	...
```

- 变着位于 `[VARIANT` 行和 `VARIANT]` 行之间，写在它所替代的那步棋的**紧后面**。
- 变着的第一步与它所替代的着法具有**相同的半回合序号和走子方**。之后在变着内部继续编号
  （9、10 …）。
- 变着内的所有着法，无论深度如何，第 1 列都用 `VA`。
- **多个备选**：在同一步棋之后紧接着依次写出多个 `[VARIANT … VARIANT]` 块。它们的顺序就是
  优先顺序。
- **嵌套变着**：`[VARIANT … VARIANT]` 块可以跟在任何 `VA` 行之后，此时它是变着内部那步棋的
  替代。深度没有限制。
- 写入程序**不得**写出空的变着（没有任何着法行的块）。
- 在结束的 `VARIANT]` 之后，主线（或上一级变着）从被替代那步棋的下一步继续。

### 3.8 在数据库中保存 XOF

整盘对局，从第一行头字段到对局分隔符，可以连同换行符一起保存在一个文本字段中。读回该字段后，
按与文件相同的方式拆分成行即可。

### 3.9 与 2025 年草案相比的变化

- 草案在着法区末尾写一行结果。**现在不再写这一行。** 结果只在 `Result` 头字段中，而且
  `Result` 现在是必需的头字段。
- 草案把 `[VARIANT … VARIANT]` 块与层级代码 `Vx` 一起使用。现在只使用 `VA`，嵌套关系由块
  本身表示。
- 推荐的中文符号表现在双方都使用简体字（帅仕相车炮马兵）。

### 3.10 完整示例

一个文件中的两盘对局（英文符号表；`→|` 表示一个制表符）：

```
Event: Example Open
Address: Hanoi
Date: 2026-11-16
Round: 1
Game Number: 1
Red Player: Player A
Blue Player: Player B
Red Team:
Blue Team:
Starting FEN: rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w - - 0 1
Result: *
Pieces Key: King = K, Assistant = A, Elephant = E, Rook = R, Cannon = C, Knight = N, Pawn = P
ECCO: B10
---------
ML→|1→|C2=5→|R→|2026-11-16 09:00:05→|Central cannon→|
ML→|2→|N8+7→|B→|2026-11-16 09:00:31→|→|
[VARIANT
VA→|2→|C8=5→|B→|→|Same-direction cannons→|
VA→|3→|N2+3→|R→|→|→|
[VARIANT
VA→|3→|N8+7→|R→|→|→|
VARIANT]
VA→|4→|N8+7→|B→|→|→|
VARIANT]
ML→|3→|N2+3→|R→|2026-11-16 09:01:10→|→|
```

## 4. 用 XOF 编程

读写 XOF 很简单。这只是文本解析，不需要编写二进制布局、转义或词法分析器。读取器只需要：

1. 在等于 18 个短横线的对局分隔符行处**把文件拆分成对局**。
2. 在 9 个短横线的区段分隔符处**把每盘对局拆分成头部和着法**。
3. **头字段：** 在冒号处拆分每一行，然后去掉两部分首尾的空白。
4. **着法：** 在制表符处拆分每一行，得到 6 列。
5. **变着：** 一个**递归函数**。当一步棋后面的行是 `[VARIANT` 时，调用该函数。它把 `VA` 行
   收集到一个列表中，直到遇到 `VARIANT]`；每当遇到另一个 `[VARIANT` 时就再次调用自身。它返回
   的每个列表都挂到该块紧前的那步棋上。

伪代码：

```
parseVariant(lines, i, parentMove):
    i = i + 1                                  # 跳过 "[VARIANT"
    list = []
    while lines[i] != "VARIANT]":
        if lines[i] == "[VARIANT":
            i = parseVariant(lines, i, last(list))   # 嵌套：对最后一步的替代
        else:
            list.add(parseMoveLine(lines[i]))
        i = i + 1
    parentMove.variants.add(list)              # 一步棋可以有多个变着
    return i                                   # "VARIANT]" 的下标
```

因此，一步棋持有一个**变着列表**，每个变着又是一个着法列表（`List<List<Move>>`），其中的着法
又可以有自己的变着。

写入则相反：写出头字段、9 个短横线的行，然后是每一行着法。在有变着的着法之后，把每个变着写成
`[VARIANT`、其着法（递归）和 `VARIANT]`。最后写 18 个短横线的行。

### 4.1 参考实现：XOFWorker（C#）

**XOFWorker** 是 [SuperXiangQi](https://superxiangqi.appsixtyone.com/) 用来读写 XOF 的开源
C#（.NET）库：

> **https://github.com/KevinDev166/XOFWorker**

| 类 | 作用 |
|---|---|
| `XOFReader` | 逐盘读取文件，每解析完一盘（以及遇到错误时）触发一个事件，因此处理大文件时无需先全部载入 |
| `XOFWriter` | 把一盘或多盘对局写入文件 |
| `XOFGame` | 一盘对局：头字段、Pieces Key 和主线着法 |
| `XOFMove` | 一行着法。`Variants` 是 `List<List<XOFMove>>`。 |
| `XOFHeader` | 一个 `Name: Value` 对 |
| `XOFPiecesKey` | Pieces Key，带有英文 / 越南文 / 中文预设 |
| `XOFKeywords` | 所有分隔符、关键字和必需头字段名集中在一处 |

递归的变着解析器是 `XOFReader.ParseVariant`。详情请参阅该项目的源代码。

XOFWorker 检查文件的**语法**。它不检查着法在棋盘上是否**合法**，因为那需要象棋着法生成器。
您的应用程序应当从 `Starting FEN` 开始重放着法并进行检查。
